01

Favorites

The first program. Per-user state in a PDA.

30 NOV 2024/Anchor 0.29 · Rust · TypeScript

An Anchor program that stores a user's favorite number, color and hobby list on chain. Each user writes into a PDA derived from their own pubkey, so accounts never collide and nobody can overwrite anyone else's record. Bounded string and vector sizes are declared up front (color capped at 50 characters, at most five hobbies) because Solana accounts are fixed-size at allocation and rent is paid on the space you reserve.

Small on purpose. It exists to get the whole loop right end to end: derive the address, size the account, write, then read it back from a TypeScript client.

  • PDA derivation
  • Account sizing
  • Anchor IDL
  • TS client

02

Cliff Chain

Token vesting with cliffs, as a monorepo.

22 DEC 2024/Anchor · Turborepo · Next.js

A vesting dApp for teams paying contributors in tokens. An organization creates a vesting account, then defines a schedule per employee with a start time, an end time, a cliff and an allocation. The program releases nothing before the cliff, then unlocks linearly, and the employee claims directly from the app.

Built as a Turborepo workspace so the Anchor program, the shared UI package and the Next.js frontend build and deploy independently. Cluster switching (devnet, testnet, localnet, custom RPC) is a first-class part of the UI rather than an environment variable, which makes demoing against a fresh validator painless.

03

Phantom Lottery

A lottery where the draw is a transaction, not a promise.

17 AUG 2025/Next.js 14 · web3.js · devnet

A lottery dApp on devnet. A one-time initialize master transaction creates the global account that holds the lottery counter and the authority, and every lottery afterwards derives its own account from that counter. Players buy tickets, entries and the prize pool live on chain, and the authority picks a winner in a transaction anyone can inspect.

The interesting part was making the setup step legible. Most of the README is spent explaining what initialization actually creates and why a program with no state cannot do anything, because that is the concept new users trip on first.

04

TalentPool

Freelance marketplace and events, with NFT proof of attendance.

25 DEC 2025/Next.js 14 · spl-token · Drizzle + Neon

Two products sharing one identity layer. Gigs: post a service, get hired peer to peer, get paid in SOL with no platform cut. Events: sell tickets in SOL, check attendees in, then mint the ticket as an NFT so attendance is portable proof rather than a row in someone's database.

On top of that sits an achievement system (event attendee, organizer, early adopter, super host, active participant) minted as SPL tokens into the user's wallet, so reputation is held by the person, not the platform. Off-chain data runs on serverless Next.js API routes over Drizzle and Neon Postgres with Zod validation at the boundary; the wallet is the login.

Charisma

Identity as a card, tribes as the graph.

27 FEB 2026/Next.js 16 · React 19 · Privy · Memo

A social app built around archetypes. You take a quiz, you get a card, the card puts you in a tribe, and the tribe gives you quests, votes and a leaderboard. 06

PayCrew

One treasury that pays humans and AI agents.

24 APR 2026/Solana Frontier 2026 · Payments

Payroll for teams that employ both contractors and models. Fiat comes in through Dodo Payments (UPI, card, bank) and converts to USDC, which lands in a Squads v4 two-of-three multisig vault. Humans are paid on a schedule; AI tools are paid per API call over x402, the HTTP 402 flow, with a monthly budget cap enforced on chain so an agent physically cannot overspend its allowance.

The security decision I care about most: every instruction in the Anchor program advances a durable nonce account atomically before doing anything else. That makes a signed payroll transaction impossible to replay, which is the exact vulnerability class behind the Drift exploit. It is built into the program, not exposed as a setting. Salary amounts are stored encrypted, mapped to the Arcium MXE integration path.

  • Durable nonce replay guard
  • Squads v4 multisig
  • x402 micropayments
  • Arcium MXE
  • Token-2022 USDC

07

Noctex

A dark pool where the matching engine never sees the order.

12 MAY 2026/Colosseum Frontier 2026 · Encrypt & Ika

Every order book on Solana publishes intent, which is why size gets front-run and why institutions route around DEXs entirely. Noctex keeps price and quantity encrypted from submit through match. Encrypt's FHE evaluates bid_price >= ask_price and min(bid_amount, ask_amount) directly on ciphertexts, so the executor computes a fill without ever holding a plaintext value.

Settlement is gated separately. The program controls an Ika dWallet under 2PC-MPC, so finalize_settlement refuses to advance until a threshold of network nodes has signed the settlement digest the program approved. FHE hides what settles, MPC decides when it settles, and neither primitive alone is sufficient: without FHE the book leaks, without MPC one compromised key drains the contract.

  • Fully homomorphic matching
  • Ika 2PC-MPC dWallet
  • Ciphertext PDAs
  • LI.FI
  • Anchor

08

Cardon

A transaction firewall for autonomous agents. Turbin3 capstone.

24 JUN 2026/Turbin3 Builders · Capstone

Give an AI agent its own keypair and it has no spend limit, no program allowlist and no human brake. One prompt injection empties the wallet. The existing answer runs the policy registry as centralized middleware, which means whoever holds code access can quietly raise a cap or delete a kill switch.

Cardon puts the control plane on chain. Every transaction the agent wants to broadcast is simulated, checked against a policy account, then signed, queued for a human, or rejected. Three account types: Agent (signing key, policy link, enabled flag, pending nonce), Policy (max lamports per transaction, human-in-the-loop threshold, daily volume ceiling, allowed programs), PendingTx (created above the threshold, closed and rent-refunded on decision). Seven instructions, split between an authority-only path and the agent's fast path.

Around the program: a Rust SDK with an async client and a simulation hook, a TypeScript SDK, a SendAI Agent Kit adapter whose wallet enforces policy on every sign, Squads v4 governance so approvals route through a multisig proposal that CPIs approve_tx, an event indexer that decodes emitted logs into an append-only audit store, a Helius webhook confirming the broadcast leg, and a Next.js approval queue.

  • Policy accounts on chain
  • Human-in-the-loop queue
  • Rust + TS SDKs
  • SendAI Agent Kit
  • Squads v4
  • Helius webhooks

09

Catenaccio

An in-play market maker that reprices before it gets picked off.

19 JUL 2026/TxODDS × Solana World Cup · Trading Tools & Agents

An autonomous market-making agent for live football markets: match result, over/under 2.5, both teams to score. It does not forecast football. It quotes two sides, earns the spread on ordinary flow, and anchors fair value to TxLINE's de-margined consensus so the price only moves when the score or the clock moves.

The whole engineering problem is the goal. Fair value gaps the instant a ball crosses the line, and anyone reading the feed faster than you takes the stale quote. Catenaccio reprices in roughly 400ms off a verified event. Backtest runs positive on average at a Sharpe of 3.16, with 36 tests behind the engine.

On chain, it does two real things on devnet: it calls the Txoracle subscribe instruction to unlock the live World Cup data tier, and it writes the decision log's 32-byte Merkle root through the SPL Memo program. That second one is the point. A trading track record nobody can audit is worth very little, so any fill can be checked against its TxLINE proof after the fact.

  • ~400ms reprice
  • Merkle-anchored decision log
  • SPL Memo
  • Txoracle subscribe
  • 36 tests

10

Foresight

Feel the goal coming before the market does. Live on mainnet.

20 JUL 2026/TxODDS World Cup · Consumer & Fan Experiences

An anticipation engine for football. It reads live odds and pitch events and lights up when on-pitch pressure surges while the betting market has not repriced yet. In the recorded walkthrough it flags a goal 207 seconds before the market moves. Watching costs nothing and needs no wallet.

Then it lets a fan prove the call. "I called it" is worthless in a group chat because everyone remembers being right; a timestamped Solana memo written before the goal is not. First-time callers sign in with Solana: connect Phantom, Solflare or Backpack and sign a free Ed25519 ownership message. The signature is verified server-side with Node's built-in crypto, wrapping the public key in an SPKI envelope, and nonces and sessions are stateless HMACs, so nothing has to be stored between requests and it survives serverless cold starts. No wallet-adapter stack at all. The server pays the memo fee, so the fan needs zero SOL for an attributed on-chain receipt.

Match stats carry a "Verified on Solana" badge backed by a live Merkle proof against TxLINE's anchored root, and unlocking the feed itself runs the on-chain Token-2022 subscribe instruction. Everything runs against mainnet-beta, smoke-tested on the production URL on every change.

  • Sign-In-With-Solana
  • Mainnet memo receipts
  • Merkle stat proofs
  • Token-2022 subscribe
  • PWA

13

Anchor Vault

A personal SOL vault, and the PDA signing trick behind it.

17 MAY 2026/Anchor · LiteSVM · Rust tests

Two PDAs per user. A state account at [b"state", user] owned by the program, holding nothing but the two bumps, so the program never pays for find_program_address on chain again. A vault at [b"vault", state] owned by the System Program, not by us.

That ownership choice is the whole design. Because the vault is a plain System account, the System Program is happy to move lamports in and out of it, so deposits are an ordinary transfer the user signs, and withdrawals are a CPI where the vault PDA signs for itself using its bump seeds. Four instructions: initialize, deposit, withdraw, close, with close draining the vault and refunding the state account's rent.

  • Signer seeds
  • System Program CPI
  • Bump caching
  • Rent refunds
  • LiteSVM

14

Anchor Escrow

Two-party SPL swap with a program-owned vault.

17 MAY 2026/Anchor 1.0 · token_interface · 8 LiteSVM tests

A maker locks a deposit of mint A into a vault owned by the escrow PDA and names a price in mint B. A taker who pays that price takes mint A and both accounts close back to the maker; if nobody takes it, the maker refunds. Three instructions, no trusted middle.

The escrow PDA is derived from [b"escrow", maker, seed], so one maker can run many escrows at once by varying the seed, which the test suite exercises directly. Token movement goes through Anchor's token_interface, so classic SPL Token and Token-2022 mints both work as long as each mint stays on one token program. Tests cover the happy paths plus zero deposit, zero receive, an underfunded taker and a refund signed by someone other than the maker.

  • Escrow PDA + vault ATA
  • Token-2022 ready
  • Account closing
  • Negative tests

15

Constant-product AMM

Pool, LP mint, swap curve, and an authority kill switch.

22 MAY 2026/Anchor 0.32.1 · devnet · Next.js 16

Anyone can open an (A, B) pool with a fee in basis points, deposit reserves for LP tokens, swap at the curve price and withdraw pro rata. First deposit mints sqrt(a * b) LP; later deposits mint proportionally to the share of reserves added. Every mutating instruction takes a slippage bound, and an optional pool authority can lock the pool, which blocks deposit, withdraw and swap in one flag.

The curve keeps the fee inside the invariant: amount_out = (in_with_fee * rB) / (rA * FEE_DENOM + in_with_fee), so k is preserved modulo the fee and the fee accrues to LPs. The math lives in its own module with unit tests separate from the integration suite. Config holds both mints, the fee, the optional authority, the lock flag and both bumps.

  • x*y=k with fees
  • LP mint PDA
  • Slippage floors
  • Checked math
  • Curve unit tests

16

NFT Staking

Freeze a Core asset in place, accrue points, mint them as tokens.

31 MAY 2026/Metaplex Core · Anchor 0.32.1 · both bonus challenges

Staking adds a FreezeDelegate plugin to the asset with frozen = true and delegates thaw rights to the asset's stake PDA, so the owner cannot move it but the program can release it later. Points accrue per second per staked asset. Claiming is its own instruction, so a holder can take rewards without unstaking, and both claim and unstake settle everything earned since the last settlement, meaning nothing is lost by claiming late. The collection carries an Attributes plugin the program updates on every stake and unstake, giving a live staked count on chain.

No published mpl-core crate lines up with Anchor 0.32.1 and Solana 3.1.x: older versions pin Solana 1.x, newer ones pull Solana 4.x types, and neither unifies with Anchor's account types. Rather than downgrade the whole toolchain, the program rebuilds the five Core instructions it needs from their Borsh layouts and discriminators and invokes them directly, so the on-chain crate depends only on anchor-lang and anchor-spl.

  • FreezeDelegate plugin
  • Hand-built Core CPI
  • Attributes plugin counter
  • Reward mint
  • Borsh discriminators

17

NFT Marketplace

Listings priced in SOL or any SPL token, plus a bidding flow.

31 MAY 2026/Metaplex Core · 9 tests · all three challenges

Listing transfers the Core asset to the listing PDA itself, so the PDA is the escrow and there is no separate vault account to reconcile. Listing.payment_mint: Option<Pubkey> denominates the sale: None means SOL, Some(mint) means an SPL token settled through transfer_checked, with mints handled as InterfaceAccount throughout so it is Token-2022 ready.

Buyers who do not want the ask can open an Offer PDA at ["offer", asset, buyer] that escrows their lamports until the maker accepts, or they cancel. Fees come out of the seller's proceeds rather than being added to the buyer's price, so the buyer always pays exactly the listed number. Every completed sale also mints reward tokens to the buyer from a marketplace-owned mint.

  • PDA-as-escrow
  • SOL + SPL pricing
  • Offer / accept / cancel
  • Treasury fee split
  • Buyer rewards

18

Instruction Introspection

Proving a sibling instruction really happened.

04 JUN 2026/Instructions sysvar · two workspaces · 13 tests

Introspection is how a program stops trusting what was passed in and starts reading what actually happened in the same atomic transaction. Both challenge options are implemented as separate Anchor workspaces. dice-bet verifies a sibling commit_result instruction carrying a custom Borsh struct signed by the house, instead of leaning on an Ed25519 signature instruction. burn-amm is an AMM that pays out only if an SPL Token Burn immediately precedes the payout instruction.

Both use the same pattern: load_current_index_checked to find yourself, load_instruction_at_checked to fetch the neighbour, then check its program ID, its discriminator and payload, its account metas and which of those accounts signed, before acting.

  • Instructions sysvar
  • Borsh payload checks
  • Account meta + signer checks
  • Burn verification

22

Solana Basics

Thirty lessons that are also a slide deck.

30 AUG 2026/137 slides · 22 diagrams · static export

A black-and-white teaching deck taking a developer from no Solana knowledge to reading the official docs unaided. Most material teaches syntax before it dislodges the model the reader arrived with, so this one goes the other way: six lessons of unlearning (the code and state split, declared accounts, signers, fees versus gas) before a line of Rust appears. Then the network underneath, the core concepts from accounts through CPI, and a SOL transfer traced end to end.

Every lesson is a readable article and a presentable deck at the same time, with a present mode, arrow-key navigation and speaker cues written to be said out loud rather than read. Lessons are typed data objects rather than markup, which is what keeps thirty of them consistent and renderable in both views.
